# Read-only PNG sequence inventory

This optional standard-library command inventories a **specified window of
original PNG frames** before or after a separate restoration/stabilisation
stage. It is extracted and adapted from the private OSF VSR source-inventory
research. It does not run SeedVR2, STAB4 or a GPU. It does not modify source
media or produce a finished master.

## Quick start

From the STAB4 repository root, create a local descriptor such as
`source.json` (adjust every field to match your own sequence):

```json
{
  "kind": "sequence",
  "path": "/data/my_source_frames",
  "frame_pattern": "f%04d.png",
  "start_frame": 0,
  "frame_count": 12,
  "width": 1920,
  "height": 1080,
  "bit_depth": 8,
  "alpha": "none"
}
```

```bash
python3 -B vsr_sequence_inventory.py source.json --receipt source-inventory.json
python3 -B -m unittest discover -s tests -p 'test_vsr_sequence_inventory.py' -v
```

The receipt is **create-only** and must be outside the source frame
directory. Omit `--receipt` to print the inventory to standard output only.
The 24 offline tests use small synthetic PNG images in temporary
directories, so no film footage or OpenCV installation is required. Three
tests simulate a frame being swapped with a symlink, a different regular
file or a FIFO during an inventory read.

## What the SHA-256 means

The `sequence_sha256` digest uses exactly the established
`OSF-VSR-SOURCE-SEQUENCE-v1` framing:

```text
OSF-VSR-SOURCE-SEQUENCE-v1
<frame_index><TAB><frame_filename><TAB><file_sha256>
...
```

where each row ends with a newline and the whole ASCII record is hashed with
SHA-256. Frame hashes cover the **entire binary PNG file**, not just pixel
payloads. Reordering, renaming, changing bytes or selecting a different
frame window can therefore change the sequence identity. The inventory
also records file size and PNG width/height/bit depth and rejects missing
frames, direct symlinks, unsafe basename formatting and incompatible
headers. The basic header check requires PNG's 13-byte IHDR payload and
ensures the declared alpha-channel presence agrees with the RGB/RGBA
colour type. RGB PNGs cannot declare straight or premultiplied alpha;
`alpha: "unknown"` is accepted with either RGB or RGBA.

**Important limits:**
- This is not a PNG decoder, CRC validation or proof of error-free pixels.
  It checks the signature and IHDR fields, not complete structural integrity.
- This is not optical-flow registration, temporal-quality evaluation,
  motion acceptance, alpha correctness or colour-pipeline verification.
- SHA-256 detects a changed file relative to a trusted reference. Hashes
  generated by an untrusted party do **not** establish its provenance.
- The returned `source_path` is an explicit local path. Do not post
  private inventory receipts publicly without reviewing and redacting
  path and source information.
- Input files and directories must remain stable while hashing. On
  POSIX systems with `O_NOFOLLOW`, each frame is opened without following
  a last-component symlink; its PNG header and full SHA-256 are taken from
  **the same regular-file descriptor**, and its final pathname identity
  must still match that descriptor. A replaced frame or substituted FIFO
  fails rather than producing a plausible receipt. Without `O_NOFOLLOW`
  support, the inventory refuses to proceed. This narrows a time-of-check
  versus time-of-use race; it is **not** a complete defence against
  adversarial mutation of ancestor directories or network filesystems.

For more robust read-only PNG sequence structure checks, including
CRC validation, see the separate [native PNG audit in OSF's ComfyUI
workflows](https://github.com/OpenSourceFilms/opensourcefilms-comfyui-workflows/blob/main/docs/audit-native-png-sequence.md).
